# Dependabot アラートの対応手順

依存の脆弱性アラートを、影響の大きさで切り分けて対応する手順です。パッケージマネージャー固有のコマンド
（依存ツリーの表示、バージョン固定の書き方）は、導入先の技術スタックに読み替えてください。
方針の背景や、ローカルに脆弱性チェックを入れるかどうかは、導入先の `CLAUDE.md`「本リポジトリの品質ゲート定義」にあります。

## 0. 前提と禁止（MUST）

- アラートの**却下・再開・コメントなど GitHub 上の変更は行わない**（外部への操作。ガードレール 12.2）。
  読み取り（`gh api` の GET）だけを行う。
- 依存の**削除・ダウングレードはしない**（12.2）。上げる場合も、言語処理系・ビルドツール・UI フレームワークなど
  **全体を左右する本体は上げず**、要確認として起票する。
- 自律ループ実行モードで行うなら、Skill `autonomous-loop` の手順（作業ブランチ・1 タスク 1 コミット・
  品質ゲート・記録の更新）に従う。
- 署名鍵を使うリリースビルドは行わない（人が行う）。署名に使う依存を上げたら、署名の検証を人へ依頼する。

## 1. アラートを取得して出どころごとにまとめる

```bash
gh api "repos/<owner>/<repo>/dependabot/alerts?state=open&per_page=100" --paginate \
  -q '.[] | [.number,.security_advisory.severity,.dependency.package.name,.dependency.manifest_path,(.security_vulnerability.first_patched_version.identifier // "-")] | @tsv' > alerts.tsv
```

- `gh` は Bash で実行する（サンドボックスの設定によっては権限の指定が要る）。一時ファイルはスクラッチパッドへ置く
  （Windows の Git Bash では `/tmp` の解決先がツールごとに異なるため使わない）。
- `manifest_path` は dependency submission を使うと実際のマニフェストと異なる値になり、**出どころの判別には
  使えないことがある**。ライブラリ単位に集計し、重大度の高い順・件数の多い順に並べて、修正版の最大値を控える。
- GitHub の push 時の表示（「n 件の脆弱性」）は集計の単位が違い、API の件数と一致しない。**API の件数を正とする**。

## 2. 出どころを切り分ける（最重要）

「配布物（アプリ・パッケージ）に入る実行時の依存か」で対応の緊急度が変わる。導入先の依存ツリー表示コマンド
（`npm ls`、`pip show`、`./gradlew dependencies` など）で、対象ライブラリがどの経路で入っているかを確かめる。

| 出どころ | 影響 | 対応 |
| --- | --- | --- |
| 実行時の依存（配布物に入る） | 利用者に届く | 最優先。版を上げる（下げない）。動作確認と検証記録への反映が要る |
| ビルド・開発ツール側（プラグイン、lint、テストの依存） | 開発・ビルド環境のみ | 第 3 節で修正版へ上げる |
| 本体（言語処理系・ビルドツール・フレームワーク）の更新が要るもの | 影響が大きい | 上げずに BACKLOG へ「要確認」で起票する |

## 3. 修正版へ上げる

1. 導入先の方式で修正版を指定する。専用の固定ファイル（例: 版の一覧ファイルを 1 つ設けてビルド定義が読む形）が
   あればそこへ追記し、無ければ依存宣言の版を直接上げる。同じ系統のライブラリ（同一プロジェクトの各モジュールなど）は
   **版をそろえる**。
2. 修正版が存在するか、互換するかは、依存の解決とビルドで分かる。存在しない版・互換しない版は失敗するため、
   上げる前に解決だけを先に流す。
3. 確認する。
   - 依存ツリーで、対象が修正版に解決される。
   - **実行時の依存が意図せず変わっていない**: 変更の前後の実行時依存の一覧を保存して `diff` する。
   - 品質ゲート（`CLAUDE.md`）をすべて実行し、ビルドが成功する。
   - メジャーに近い更新は、それを使うツールが動くことまで確かめる。

## 4. 記録する

- BACKLOG（`FORMAT.md` に従う）: 解消したものは `EXECUTE.md` と `CHANGELOG.md` へ記録して削除する。
  保留（要確認）は理由とアラートの重大度を書いて残す。GitHub 上のマージ後の再評価の確認は
  **人手検証**（担当 ユーザー）として起票する（アラートが閉じるのは、マージ後に依存の再解析が走った後のため）。
- 設計書（`DESIGN.md`）の依存の脆弱性に関する節へ、件数・出どころ・上げた版・保留したものを残す
  （時点情報は日付付きで）。

## 5. よくある落とし穴

- **ライブラリを上げると、その依存が新しいアラートとして現れることがある。** マージ後にアラートを取り直して、
  残りと新規を同じ手順（1〜4）でもう一度流す。
- アラートの件数は、ツール側のライブラリが 1 つ上がっても**マージして依存の再解析が走るまで減らない**。
  ローカルで件数が変わらないことを失敗と判断しない。
- 前回の対応の根拠となった確認結果（実行時の依存に該当なし）を、**新しいアラートへ当てはめて省略しない**。
  毎回第 2 節で確かめる。
